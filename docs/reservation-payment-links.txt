Existing manual reservation payment links — implementation / rollout checklist
Base: main c6cd9f7f395cd2dd831ff6ebd8b7488b21253027 (matched live Render on 2026-10-15).

Scope
- Full settlement of an unpaid, confirmed, direct reservation with an existing
  Hostaway ID and BookingIntent. No new inventory reservation or availability quote.
- Existing verified or uncertain collections, refund obligations and active/completed
  amendments are blocked for review. Price-difference collection is NOT in this release.
- HyperBill and the existing accounting fallback are unchanged when the new flag is off.

Activation (NOT performed by this implementation)
1. Approve rollout and link policy, review the branch against current main, run CI with
   PostgreSQL including concurrency tests, and inspect the change set.
2. Apply payments migrations 0010-0012 during the separately approved deployment.
   The loyalty backup closure includes payment requests and delivery evidence. Validation
   supports exactly the current schema and the pre-payment-link schema (only the nullable
   PaymentAttempt.payment_request field and two new models differ). Historical seals and
   payloads are not rewritten; all existing closure/history checks still run. Offline
   old-to-new mirror transition is tested; unknown older schemas remain rejected. A real
   backup destination read/write was not performed and must be checked on approved rollout.
3. Keep RESERVATION_PAYMENT_LINKS_ENABLED=false until web AND worker run this version.
4. Deploy the dispatch-only scheduler version; it requires no payment credentials.
5. Review SITE_BASE_URL (HTTPS origin), HYPERPAY environment/credentials, UltraMsg,
   and future-only Hostaway financial receipt settings via approved private channels.
   Never print secrets or use production credentials in local tests.
6. The configurable RESERVATION_PAYMENT_LINK_TTL_SECONDS default is 86400 seconds,
   additionally capped by actual check-in time in the property's timezone. An expired
   provisional quote/intent cannot reprice an already-confirmed stay; the request freezes
   the approved amount. Same-day requests remain allowed before actual arrival, not
   rejected at midnight. Obtain owner approval for
   that policy before enabling. Expiring/revoking the local link does NOT cancel a stay
   or invalidate an already-open provider checkout; unresolved attempts prevent replacing
   or revoking the request. A late verified payment is retained, not discarded.
7. The application console, Django server and Gunicorn access log redact bearer payment
   paths and return tokens. Review upstream/proxy log retention before exposing links;
   these server-side filters do not control edge-provider logs. Code does not retain message bodies,
   bearer links or raw gateway responses. Link pages disable Google integrations and send
   no-referrer, no-store and noindex headers. Payment-only access never grants management.
8. Enable only after explicit approval; run one authorized end-to-end trial and match
   provider amount/transaction, local state, Hostaway financial entry and guest delivery.

Architecture
- ReservationPaymentRequest freezes original amount/currency plus SAR amount and a
  fingerprint of booking/guest/FX data. Deterministic signed links grant payment only.
- Opening a link has no provider side effect. Guest POST requires CSRF, current document
  digest, terms/house-rules acceptance and a real billing address. Guest identity remains
  the existing reservation identity, not editable through a bearer link.
- Checkout validates the existing Hostaway reservation and paid charges, then serializes
  local claims on reservation/intent/request rows. The local attempt commits before the
  gateway POST. A lost response is REVIEW, never blindly retried.
- The same gateway, widget, integrity validation and allowed payment brands are reused.
  Success is routed to existing-reservation completion, never Hostaway booking creation.
- The worker polls persisted checkout IDs, including after link expiry/feature rollback.
  It can recover financial success persisted just before a process crash. A changed or
  cancelled booking with a late payment is flagged for review, not silently reopened.
- The same existing worker sends durable WhatsApp link/receipt records. A send timeout or
  process crash while sending is unknown/sending and requires review; no automatic resend.
  Each explicit operator resend reuses the same URL without a cooldown. Background
  recovery and the payment receipt remain idempotent; resend never extends link expiry.
- Financial receipt uses the frozen source amount/currency in Hostaway (e.g. MAD), with
  the actual SAR gateway charge retained separately. It never relabels SAR as MAD.
- No new paid resources, global queue purge, Blueprint sync, or credentials for beat.

Recovery / rollback
- If provider verification is unavailable, do not collect again. Retry authoritative GET
  via worker, or inspect the payment attempt with operations access.
- Existing local review/unknown attempts block new checkout creation. Accounting must
  reconcile provider outcomes; never reset them just to enable another payment.
- Switch the rollout flag off to stop new public links/checkouts. Keep the gateway,
  worker, schema and recovery task available for outstanding payments. Do not reverse the
  migration or remove its records after use. Card details are never stored; the existing
  intent fields retain the guest-entered billing address.
- Disabling new links restores the original manual-accounting request for NEW bookings;
  do not send an additional accounting link for an unresolved payment already in progress.

Acceptance
- No second BookingIntent/Reservation/Hostaway creation, even on refresh/retry.
- Price fixed by administration; no reprice or availability request on collection.
- Anonymous recipient can pay; cannot manage/cancel/claim booking via the bearer link.
- Amount/currency/reference/type/brand and nonempty financial payment ID are verified.
- Cancellation, tampering, expiry, stale legal forms, prior/parallel collections, lost
  checkout response, repeated callbacks and closed-browser recovery are covered in tests.
- Live collection, real WhatsApp delivery, provider configuration, full/partial refund,
  cross-currency amendment/refund settlement, tracking conversions and production rollout
  are NOT proven by mocked tests. Cross-currency future amendments retain existing review guards.

Existing-booking / offline receipt extension — 2026-10-15
- Existing direct bookings with a matching local BookingIntent/FX snapshot can issue a
  payment link from booking administration without requiring a ManualBookingDraft.
  OTA/external-channel collections are blocked. Imported bookings without an intent
  are not silently converted into website checkouts; do not fabricate guest/FX data.
- MANUAL_PAYMENT_RECEIPTS_ENABLED defaults false, independent of card collection.
  Approved operations managers can attest a FULL bank/cash payment in original booking
  currency, with received time, proof reference, optional note and explicit confirmation.
  A frozen reservation digest rejects stale amounts/dates. No partial/mixed settlement.
- OfflinePaymentReceipt holds the manager's evidence and links to a provider=manual
  accounting record when an existing intent exists. manual: identifiers are INTERNAL
  receipt references, never HyperPay transaction IDs. No intent is invented for imports.
- Settlements/refund ceilings count the receipt once. Bank/cash refunds remain manual,
  never a HyperPay refund or claimed gateway authorization. Issued invoices are unchanged;
  no invoice/email/WhatsApp is auto-sent by the offline receipt action.
- Shared ManualReceiptReference PK claims unify old loyalty and new administration
  receipt references, including case/Unicode normalization. Migration 0012 backfills
  legacy manual payment references and stops on historical collisions for accounting
  review. It does not rewrite old payments or choose a conflicting winner silently.
- Receipt recording locks reservation then intent, blocks existing/uncertain collections,
  revokes unused links and leaves the original stay unchanged. Parallel cash/cash and
  cash/online claims are tested on PostgreSQL CI, not inferred from SQLite.
- Lodging-only owner attestation is optional and auditable. It permits loyalty allocation
  for a manually overridden lodging-only rate even when intent equals booking but the
  original quote breakdown differs. Fees are never automatically assumed to be lodging.
- This release records offline money LOCALLY. It neither calls a bank nor writes an
  offline Hostaway charge. The operations UI says so explicitly; future provider sync
  must be separately gated, deduplicated and tested before it is represented as complete.
- Majed Alzahrani was nominated by the owner for a future live trial; no live record,
  amount, phone, inventory or message has been fetched, modified or sent for that trial.

Optional accountant route — 2026-10-15
- The default new-manual-booking button still creates the stay and queues the latest
  branded guest payment link. A secondary, collapsed option explicitly chooses an
  accountant request INSTEAD of creating/sending the website payment link.
- Existing unpaid confirmed direct/manual bookings expose the same optional request.
  Rendering a page or failing guest delivery never triggers the accountant route.
- An open/review/paid website request must be resolved/revoked explicitly first.
  Successful or unresolved gateway attempts block the accountant request, including
  after link expiry/revocation. No automatic reservation cancellation or price change.
- The optional sender claims its existing auditable accounting delivery under the
  same reservation lock used by website link issuance. Once accounting is claimed,
  new site links are blocked for review because the site cannot revoke or verify an
  external payment link. No automatic route switch-back is implied.
- Requests to accounting retain the existing single-send rule: uncertain/failed/sent
  requests are not blindly resent. The owner's unrestricted guest-link resend policy
  is unchanged. Provider acceptance is not handset delivery or guest payment proof.
- No schema, secrets, infrastructure, refunds or live messages change in this patch.
